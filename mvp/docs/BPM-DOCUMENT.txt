3. REGIME DETECTION (Process P2)
================================================================================

Source: src/engine/regime.ts

Two-stage detection: Base regime from daily closes, then Enhanced with
market signals.

--- STAGE 1: BASE REGIME (detectRegime) ---

Input: daily closing prices from getDailyCloses(db, regimeWindowDays)
       (default 7 days)

  (XOR Gateway: prices.length < 3?)
  --yes--> Return 'RANGING' (insufficient data)
  --no--> continue

  Calculate:
    netMove = |lastPrice - firstPrice|
    totalPath = sum of |prices[i] - prices[i-1]| for all i
    dirRatio = netMove / totalPath  (0 = choppy, 1 = straight line)
    logReturns = log(prices[i] / prices[i-1])
    realisedVol = stdDev(logReturns)

  Decision tree:
    (XOR: realisedVol > 0.08 OR !isFinite?)
    --yes--> EXTREME
    --no--> (XOR: dirRatio > trendThreshold?)  [default 0.35]
            --yes--> (XOR: lastPrice > firstPrice?)
                     --yes--> BULLISH_TREND
                     --no--> BEARISH_TREND
            --no--> RANGING

--- STAGE 2: ENHANCED DETECTION (detectRegimeEnhanced) ---

Input: base regime result + MarketSignals from MarketDataService

  If no market signals available: return base regime with confidence=0.

  Step 1b: Vol4h refinement
    - If base=EXTREME but vol4h < threshold*0.8: DOWNGRADE to trend/ranging
      (base EXTREME from sparse daily data was misleading)
    - If base!=EXTREME but vol4h > threshold: UPGRADE to EXTREME
      (base missed it with few daily closes)

  Step 2: EXTREME override — 1h vol spike
    If vol1h > vol1hExtremeThreshold (0.06): -> EXTREME, confidence++

  Step 3: EXTREME override — 4h vol + volume spike
    If vol4h > threshold AND volumeRatio4h > volumeSpikeMultiple (3x):
    -> EXTREME, confidence++

  Step 4: TREND override — large SOL move + volume
    If |solDelta24h| > trendDeltaThreshold (4%) AND volumeRatio4h > 2x
    AND current regime is RANGING:
    -> BULLISH_TREND or BEARISH_TREND based on sign

  Step 5: BTC correlation check
    If |btcDelta24h| > btcCorrelationThreshold (3%) AND same direction
    as SOL: confidence++

  Step 6: Fear & Greed tiebreaker
    - F&G < 25 (extreme fear): confirms BEARISH/EXTREME, confidence++
      Can override RANGING -> BEARISH if SOL dropping > 2%
    - F&G > 75 (extreme greed): confirms BULLISH, confidence++
    - F&G 40-60 + RANGING: confidence++

  Step 7: Volume confirms regime
    - Low volume + RANGING: confidence++
    - High volume + trending/extreme: confidence++

  Output: {regime, baseRegime, overrideReason, confidence (0-5), signals}

--- PRIORITY CHAIN ---

  Highest priority first:
  1. 1h vol spike -> EXTREME (immediate danger)
  2. 4h vol + volume spike -> EXTREME
  3. vol4h refinement of base EXTREME (can downgrade or upgrade)
  4. SOL delta + volume -> TREND override
  5. F&G extreme fear + SOL drop -> BEARISH override
  6. Base regime from daily closes (lowest priority, can be overridden)

--- REGIME CHANGE SUPPRESSION ---

  A regime change is only applied if:
  - Daily closes >= 5 (MIN_CLOSES_FOR_REGIME_CHANGE), OR
  - Market signals produced an override (overrideReason != null), OR
  - Market signals confirm with confidence > 0

  This prevents flapping on thin data.

4. POSITION LIFECYCLE (Process P3)
================================================================================

Source: src/main.ts (liveOpenPosition, liveClosePosition, liveCloseAndReopen)

--- SUBPROCESS 3.1: OPEN POSITION ---

  Trigger: liveOpenPosition(price, eventType, reason)

  [TX Backoff Check]
  (XOR: Date.now() < txBackoffUntil?)
  --yes--> [Skip — exponential backoff active]
  --no--> continue

  Step 1: Calculate range
    params = runtime.regimeParams[liveRegime]
    If rangeWidthOverride != null, use override
    range = calcRange(price, params) -> {tickLower, tickUpper, priceLower, priceUpper}

  Step 2: Calculate deploy amount
    totalWalletUsdc = sol * price + usdc
    reserveUsdc = solReserve * price + usdcReserve
    deployUsdc = min(total * deployPct, total - reserve)
    (XOR: deployUsdc < $5?) --yes--> [Abort — insufficient funds]

  Step 3: Execute on-chain (executor.openPosition)
    a) Fetch pool state (IGNORE_CACHE)
    b) Init tick arrays if needed (retry once on failure)
    c) Get wallet balances, compute ideal SOL/USDC ratio for range
    d) PRE-OPEN SWAP (if wallet heavily imbalanced):
       - If USDC < $5 and SOL > 0.1: swap SOL -> USDC
       - If SOL < 0.01 and USDC > $10: swap USDC -> SOL
       Uses Jupiter (Orca fallback). Wait 4s for confirmation.
    e) DEPLOY CAP: cap available capital at deployUsdc
       (prevents depositing more than regime allows)
    f) QUOTING:
       - Try SOL-based quote first
       - If SOL quote needs more USDC than available, try USDC-based
       - Reserve 0.02 SOL extra for rent + TX fees
    g) Open position TX (whirlpool.openPosition)
    h) Record: positionMint, entryPrice, entryTime, regime, entrySol, entryUsdc

  Step 4: Post-open
    - Reset consecutiveTxFailures, txBackoffUntil
    - Increment liveRebalancesThisHour, dailyRebalanceCount
    - Set liveBotState = ACTIVE
    - Auto-enable autoDeploy if deposited < 50% of target
    - Log POSITION_OPENED event
    - Set idleRebalancePending = true

  [Error boundary: TX failure]
  - consecutiveTxFailures++
  - txBackoffUntil = now + min(300, 60 * 2^(failures-1)) seconds
  - Backoff sequence: 60s, 120s, 240s, 300s (cap)

--- SUBPROCESS 3.2: CLOSE POSITION ---

  Trigger: liveClosePosition(price, eventType, reason)

  Step 1: Capture position ID before close
  Step 2: Capture wallet balances before close
  Step 3: executor.closePosition()
    a) Get pending fees (collectFeesQuote from on-chain tick arrays)
    b) Compute IL: ilPct = 2*sqrt(r)/(1+r) - 1, where r = currentPrice/entryPrice
    c) Capture position info (mint, range)
    d) Get wallet balances before
    e) whirlpool.closePosition() — may produce multiple TX builders
       Execute each via execTx() (with retry on transient errors)
    f) CRITICAL: Only clear currentPosition AFTER all TXs succeed
       (crash-safe: if TX fails, position state is preserved)
    g) Get wallet balances after
    h) Return: {solReceived, usdcReceived, fees, il, entryPrice, closePrice}

  Step 4: Accumulate cumulative fees and IL
    liveCumFeesSol += feeSolCollected
    liveCumFeesUsdc += feeUsdcCollected
    liveRealizedIl += ilAtClose

  Step 5: Log event, reset backoff counters

--- SUBPROCESS 3.3: CLOSE AND REOPEN ---

  Trigger: liveCloseAndReopen(price, eventType, reason)

  Step 1: liveClosePosition()
    (XOR: close succeeded?)
    --no--> [Abort — "position still open", do NOT attempt reopen]
    --yes--> continue

  Step 2: Wait 2s (let on-chain state settle)

  Step 3: RE-CHECK REGIME before reopening
    Fresh detectRegimeEnhanced() call
    If regime changed: update liveRegime, log REGIME_CHANGE
    Reset liveLastRegimeCheck

  Step 4: liveOpenPosition() with new regime params

  Step 5: IMMEDIATE DB SAVE of new position
    (prevents orphan recovery from killing a legitimate position
     if bot crashes before next cycle save)

  Step 6: Set idleRebalancePending = true

--- SUBPROCESS 3.4: PULLBACK WATCH ---

  State: liveBotState = WAITING_PULLBACK
  Variables: livePullbackActive, livePullbackPeak, livePullbackStart

  Entry conditions (two paths):
  1. T1_UPSIDE: Rule 2 early upside exit triggered
  2. OOR_ABOVE: Price fully out of range above

  Per-cycle logic when in pullback watch:

  [Flash Crash Cooldown Gate]
  (XOR: now < liveFlashCrashCooldownUntil?)
  --yes--> [Return — still in cooldown]
  --no--> continue

  [Flash Crash Detection]
  (XOR: isFlashCrash(liveRecentPrices)?)
  --yes--> Set cooldownUntil = now + flashCrashWaitMinutes * 60000
           Reset peak to current price
           Reset timeout start to now
           Persist cooldownUntil to DB config
           [Return]

  [Re-entry Decision]
  shouldReenterAfterUpside(currentPrice, peakPrice, watchStartTime, now)

  (XOR: pullbackPct >= pullbackThresholdPct?)   [default 2.5%]
  --yes--> {should: true, reason: 'PULLBACK'}

  (XOR: hoursWaiting >= timeoutHours?)           [default 4h]
  --yes--> {should: true, reason: 'TIMEOUT'}

  --no--> {should: false, reason: 'WAITING'}
          Track peak: if price > livePullbackPeak, update peak

  On re-entry:
    livePullbackActive = false
    liveFlashCrashCooldownUntil = 0
    liveOpenPosition(price, 'PULLBACK_REENTRY', reason)
    idleRebalancePending = true

5. RULE EXECUTION (Process P4)
================================================================================

Source: src/engine/rules.ts
Each rule is parameterized by the current regime via REGIME_PARAMS.

--- R1: RANGE CALCULATION (calcRange) ---

  Input: currentPrice, RegimeParams, priceToTick converters
  Output: RangeBounds {tickLower, tickUpper, priceLower, priceUpper}

  Formula:
    lower = currentPrice * (1 - rangeWidthPct/100 * skewDown)
    upper = currentPrice * (1 + rangeWidthPct/100 * skewUp)

  Tick alignment:
    tickLower: priceToTickLower(lower) — rounds DOWN
    tickUpper: priceToTickUpper(upper) — rounds UP
    (ensures range is never narrower than intended)

  Regime defaults:
    RANGING:       1.5% width, 30% down / 70% up
    BULLISH_TREND: 3.0% width, 20% down / 80% up
    BEARISH_TREND: 2.5% width, 40% down / 60% up
    EXTREME:       6.0% width, 50% down / 50% up

  Optional: rangeWidthOverride replaces rangeWidthPct if set.

--- R2: PROXIMITY MONITORING (calcProximity, shouldFireDownside, shouldFireUpside) ---

  calcProximity:
    centre = (priceLower + priceUpper) / 2
    halfWidth = (priceUpper - priceLower) / 2
    proxToLower = max(0, (centre - currentPrice) / halfWidth)   [0=center, 1=edge]
    proxToUpper = max(0, (currentPrice - centre) / halfWidth)
    inRange = currentPrice in [priceLower, priceUpper]

  Trigger conditions:
    shouldFireDownside: proxToLower >= proxThresholdLower
    shouldFireUpside:   proxToUpper >= proxThresholdUpper

  Regime thresholds:
    RANGING:       lower 65%, upper 88%
    BULLISH_TREND: lower 70%, upper 92%
    BEARISH_TREND: lower 55%, upper 82%
    EXTREME:       lower 50%, upper 80%

  Toggled by rule2Enabled flag (DB rule_toggles table).
  When disabled: positions only close on full OOR (out of range).

--- R3: PULLBACK RE-ENTRY (shouldReenterAfterUpside, isFlashCrash) ---

  Purpose: After upside exit, wait for price pullback before re-entering.

  shouldReenterAfterUpside:
    pullbackPct = (peakPrice - currentPrice) / peakPrice * 100
    hoursWaiting = (now - watchStartTime) / 3600000

    If pullbackPct >= runtime.pullbackThresholdPct (default 2.5%):
      -> Re-enter (PULLBACK reason)
    If hoursWaiting >= runtime.timeoutHours (default 4h):
      -> Re-enter (TIMEOUT reason)
    Else: WAITING

  isFlashCrash:
    Computes max drawdown (peak-to-trough) in price window.
    NOT endpoint-to-endpoint — a 5% drop + 3% recovery = 5% crash.
    Threshold: runtime.flashCrashPct (default 5%)

  Flash crash behavior:
    - Block re-entry for flashCrashWaitMinutes (default 15min)
    - Reset peak to crash price
    - Reset timeout start
    - Cooldown persisted to DB (survives restart)

--- R4: RE-ENTRY SPLIT (getDownsideReentrySplit) ---

  Returns the regime-specific SOL re-entry split ratio.
  Used to determine how to split capital on downside re-entry.

    RANGING:       50% SOL
    BULLISH_TREND: 50% SOL
    BEARISH_TREND: 30% SOL
    EXTREME:       20% SOL

--- R5: POSITION SIZING + DEPLOY CAP (getDeployAmount, checkAutoDeploy) ---

  getDeployAmount:
    deployUsdc = totalCapital * deployPct
    reserveUsdc = totalCapital * (1 - deployPct)

  Deploy percentages by regime:
    RANGING:       100%
    BULLISH_TREND: 85%
    BEARISH_TREND: 75%
    EXTREME:       25%

  Deploy cap enforcement (in executor.openPosition):
    availableValueUsdc = solAvail * price + usdcAvail
    if availableValueUsdc > usdcToDeposit:
      scale down solAvail and usdcAvail proportionally

  Capital guard: runtime.maxLiveCapitalUsdc (default $5000)
    Validated at startup via validateWalletForLive().

--- R6: FEE HARVEST (isHarvestDue, calcHarvestFees, collectFees) ---

  isHarvestDue:
    daysSinceHarvest = (now - lastHarvestTime) / 86400000
    Return: daysSinceHarvest >= harvestIntervalDays

  Harvest intervals by regime:
    RANGING:       7 days
    BULLISH_TREND: 4 days
    BEARISH_TREND: 2 days
    EXTREME:       1 day

  Harvest execution:
    1. Check pending fees >= $0.50 (skip if too small for gas ~$0.10)
    2. collectFees() — on-chain TX to claim accrued fees
    3. SOL fee conversion:
       Convert harvestSolConvertPct of SOL fees to USDC via swap
       RANGING: 0% (keep SOL), BULLISH: 70%, BEARISH: 100%, EXTREME: 100%
       Gas reserve check: ensure minSolForGas remains after conversion
    4. Update cumulative fee trackers

  Harvest check gate: every 1 hour (liveLastHarvestCheck)

--- R7: AUTO CAPITAL DEPLOYMENT (checkAutoDeploy) ---

  Purpose: Deploy idle wallet funds into existing position.
  Check interval: every autoDeployCheckMinutes (default 5min).
  Cooldown: autoDeployCooldownMinutes (default 30min).

  Decision chain (BR = Business Rule):

  BR-0: Enabled check (autoDeployEnabled toggle)
  BR-3: Block in EXTREME regime (survival mode, 25% cap is deliberate)
        BEARISH is allowed — deploy cap limits exposure.
  BR-1: Minimum idle funds: SOL >= minIdleSol OR USDC >= minIdleUsdc
  BR-6: Cooldown: minSinceLast < cooldownMin? Skip.
  BR-3: Capital cap headroom: maxDeployUsdc - positionValueUsdc >= minDeployUsdc
  BR-4: Dust check: deployableUsdc >= minDeployUsdc (default $10)
  BR-2: Price in range check: deviation from range midpoint <= 1
        Plus: not too close to edges (deviation < 1 - deployRatioTolerance)

  Execution if shouldDeploy:
    liveExecutor.increaseLiquidity(price, deployableUsdc)
    (swap to match ratio, cap at deploy target, quote, increase liquidity TX)

--- R8: IDLE WALLET REBALANCE ---

  Purpose: Maintain target SOL/USDC split in idle wallet per regime.

  Trigger conditions (OR):
    - Regime changed (lastIdleRebalanceRegime != liveRegime)
    - idleRebalancePending after position reopen (with 30min cooldown)

  Target SOL percentages:
    RANGING:       50% SOL
    BULLISH_TREND: 60% SOL
    BEARISH_TREND: 35% SOL
    EXTREME:       15% SOL

  Execution:
    1. Get idle capital (wallet - reserves)
    2. If idleTotal < idleRebalanceMinUsdc ($100): skip
    3. Compute currentSolPct vs targetSolPct
    4. If |deviation| <= idleRebalanceDeviationPct (15%): skip (near target)
    5. Swap via doSwapPublic (Jupiter, Orca fallback)
       - SOL excess: swap SOL -> USDC (min 0.01 SOL, $5 value)
       - USDC excess: swap USDC -> SOL (min $1, $5 value)

6. MARKET DATA PIPELINE (Process P5)
================================================================================

Source: src/data/oracle.ts, src/data/market.ts, src/data/pool.ts

--- ORACLE (Pyth Hermes) ---

  Service: OracleService (src/data/oracle.ts)
  Feed: SOL/USD Pyth price feed
  Polling: every 2 seconds via setInterval

  Data flow:
    Hermes API (getLatestPriceUpdates) -> handlePriceUpdate() -> lastPrice

  Validation pipeline (each price update):
    1. Staleness: ageSec = now - publishTime; reject if > maxStalenessSec (60s)
    2. Positive price: reject if <= 0 or !isFinite
    3. Confidence: confidencePct = (conf / price) * 100;
       reject if > maxConfidencePct (0.5%)

  On rejection: badPriceCount incremented, logged as warning.

  getPrice() returns null if:
    - No price received yet
    - Last update older than maxStalenessSec

--- MARKET DATA (CoinGecko + Alternative.me) ---

  Service: MarketDataService (src/data/market.ts)
  Polling: every 15 minutes via setInterval
  Re-entrance guard: this.refreshing flag prevents concurrent fetches

  Data sources (fetched sequentially with 10s timeouts each):
    1. CoinGecko OHLC (days=1): ~30min candles -> vol1h (stddev of log returns)
       Also derives solDelta24h from endpoint prices
    2. CoinGecko OHLC (days=7): 4h candles -> vol4h (stddev of log returns)
    3. CoinGecko simple/price: SOL 24h price change, 24h volume
    4. CoinGecko market_chart (7d): volume ratio (latest / 7d average)
    5. CoinGecko simple/price (BTC): BTC price and 24h change
    6. Alternative.me Fear & Greed Index: 0-100 value + label

  Output: MarketSignals object with all data + errors array
  Graceful degradation: each API call is independently try/caught.
  Missing signals = null (enhanced regime detection handles nulls).

--- POOL STATE (Orca Whirlpool) ---

  Service: PoolService (src/data/pool.ts)
  Cache TTL: 10 seconds
  Fetched: on-demand via fetchState() (called each decision cycle)

  Data: tickCurrentIndex, sqrtPriceX64, liquidity, feeRate
  Error handling: on fetch error, returns cached state with updated timestamp
  (prevents rapid retry loops)

  Tick utility functions:
    priceToTick(price) -> initializable tick index
    priceToTickLower(price) -> rounded DOWN (for lower bounds)
    priceToTickUpper(price) -> rounded UP (for upper bounds)
    tickToPrice(tick) -> price

7. STATE MACHINE
================================================================================

Source: src/types.ts (BotState type), src/main.ts (transitions)

States:
  IDLE              — No position, bot ready to open
  ACTIVE            — Position open, monitoring and earning fees
  WAITING_PULLBACK  — No position, watching for price pullback after upside exit
  HALTED            — Bot stopped, no actions taken (runLiveCycle returns immediately)
  REBALANCING       — (Defined in types but not used in live code; reserved)

                    +---------------------------------------------+
                    |              STATE TRANSITIONS               |
                    +---------------------------------------------+

  +--------+   open position   +---------+
  | IDLE   |------------------>| ACTIVE  |
  +--------+                   +---------+
      ^                            |
      |  flash crash OOR_BELOW     |  T1_DOWNSIDE (close+reopen)
      |  (close, no reopen)        |  -> stays ACTIVE (reopened)
      |                            |
      |  resume from pullback      |  OOR_BELOW (close+reopen)
      |  timeout/pullback reached  |  -> stays ACTIVE (reopened)
      |                            |
      |                            |  position max age
      |                            |  -> stays ACTIVE (close+reopen)
      |                            |
      |                            |  T1_UPSIDE
      |                            |  -> WAITING_PULLBACK
      |                            |
      |                            |  OOR_ABOVE
      |                            |  -> WAITING_PULLBACK
      |                            |
      |                            |  dashboard close/emergency
      |                            |  -> IDLE (paused)
      |                            |
      |  +-------------------+     |
      +--| WAITING_PULLBACK  |<----+
      |  +-------------------+
      |       |      ^
      |       |      | flash crash -> cooldown, reset peak/timeout
      |       |      | price > peak -> update peak
      |       |
      |       | pullback >= threshold OR timeout >= hours
      |       v
      +-- open position -> ACTIVE
          (via PULLBACK_REENTRY)

  +---------+
  | HALTED  |  <-- (not triggered programmatically; reserved for future use)

    - Pause:          ACTIVE -> IDLE (botPaused = true)
    - Resume:         IDLE -> ACTIVE (botPaused = false)

8. ERROR HANDLING & SAFETY (Process P6)
================================================================================

--- 8.1: TX FAILURE -> EXPONENTIAL BACKOFF ---

  Variables: consecutiveTxFailures, txBackoffUntil

  On any TX failure (open or close):
    consecutiveTxFailures++
    backoffSec = min(300, 60 * 2^(failures-1))
    txBackoffUntil = now + backoffSec * 1000

  Backoff schedule:
    1st failure:  60s
    2nd failure: 120s
    3rd failure: 240s
    4th+ failure: 300s (5min cap)

  Reset on success: consecutiveTxFailures = 0, txBackoffUntil = 0

  Check before any position operation:
    if (Date.now() < txBackoffUntil) -> skip with log

--- 8.2: TRANSIENT TX RETRY ---

  In executor.execTx():
    If TX fails with "Blockhash not found" / "timeout" / "429":
      Wait 3s, retry once
    Other errors: throw immediately

--- 8.3: FLASH CRASH DETECTION ---

  isFlashCrash(prices): max peak-to-trough drawdown >= flashCrashPct (5%)
  Computed over last 10 price samples (~10 minutes at 60s intervals).

  Two trigger points:
  1. During pullback watch: resets peak, resets timeout, enters cooldown
  2. During OOR_BELOW: closes position without reopen, enters cooldown

  Cooldown: flashCrashWaitMinutes (default 15min)
  Persisted: flashCrashCooldownUntil saved to DB config table
  (survives bot restart)

--- 8.4: CIRCUIT BREAKERS ---

  Defined in constants.ts RISK:
    DAILY_LOSS_LIMIT_PCT:      5%
    WEEKLY_DRAWDOWN_LIMIT_PCT: 15%
    MAX_IL_PCT:                8%
    REBALANCE_LOOP_LIMIT:      10 per hour

  Rebalance rate limit: enforced in runLiveCycle()
    if liveRebalancesThisHour >= rebalanceLoopLimit -> return
    Counter resets every hour.

  Note: Daily/weekly loss limits and MAX_IL_PCT are defined but not
  programmatically enforced as auto-halt triggers in current code.
  They serve as operator monitoring thresholds.

--- 8.5: CRASH RECOVERY FROM DB ---

  On startup (src/main.ts, main()):

  1. Restore bot state from bot_state table (row id=1):
     - liveBotState, liveRegime, liveCumFeesSol, liveCumFeesUsdc,
       liveRealizedIl, gas stats
     - pullback state: pullback_active, pullback_peak, pullback_start
     - liveLastHarvestTime

  2. Restore position from position_json:
     - If valid JSON with positionMint: reconstruct LivePosition
     - Set liveBotState = ACTIVE
     - Log RESTORED decision

  3. Orphaned position recovery:
     - If no position in DB: scan all wallet token accounts
     - Look for NFT-like tokens (amount=1, decimals=0) that are
       Whirlpool position PDAs
     - Close any found orphans, log recovery

  4. Flash crash cooldown restored from DB config table

  Critical safety: closeAndReopen saves position to DB IMMEDIATELY
  after reopen (before next cycle), preventing orphan recovery from
  killing a legitimate new position.

--- 8.6: GRACEFUL SHUTDOWN (SIGINT) ---

  On Ctrl+C:
    1. clearInterval(decisionLoop)
    2. oracle.stop(), marketData.stop(), reporter.stop(), dashboard.stop()
    3. Save current state to DB (position, fees, IL, gas, pullback)
    4. process.exit(0)

  Emergency Stop (dashboard):
    1. Stop all intervals and services
    2. Close position if open (with fee collection)
    3. Save state to DB
    4. Exit after 3s

APPENDIX B: SWAP SYSTEM
================================================================================

Source: src/live/swapper.ts, src/live/jupiter.ts

Provider strategy (runtime.swapProvider):
  'jupiter'          — Jupiter V6 aggregator only
  'orca'             — Orca Whirlpool swap only
  'jupiter-fallback' — Jupiter first, Orca fallback (DEFAULT)

Jupiter:

  - Swap API: https://api.jup.ag/swap/v1/swap

  - Slippage: runtime.swapSlippageBps (default 6 bps = 0.06%)
  - Gas tracked separately (feeLamports from TX confirmation)

Orca:
  - Direct pool swap via swapQuoteByInputToken + whirlpool.swap
  - Gas tracked via execTx() wrapper
  - Slippage: same as Jupiter

Swap use cases:
  1. Pre-open swap: balance wallet before position opening
  2. Add liquidity swap: match position ratio before deposit
  3. Harvest SOL conversion: convert harvested SOL fees to USDC
  4. Idle wallet rebalance: maintain target SOL/USDC split
